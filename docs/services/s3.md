crash recovery) built — bucket CRUD, single-request object
PUT/GET/DELETE/HEAD, and AWS-shaped multipart upload, wire-compatible
with AWS S3's REST API (path-style). Java/Spring Boot implementation,
per the 2026-08-19 language pivot in `architecture.md` §3. See

## Scope

- Buckets: create/list/delete, per-bucket policy attachment
- Objects: PUT/GET/DELETE/HEAD; byte-range GET (deferred)
- Multipart upload: initiate → upload parts → complete/abort, **with
  crash recovery** (kill mid-upload, verify clean retry or orphan
  cleanup — the best interview anecdote in the project) — built, see
  below
- Versioning: keep prior versions, list, restore (deferred)
- Metadata: content-type; custom tags (deferred)

## Tech stack

- Java 21, Spring Boot (Spring MVC + virtual threads), Maven
- Spring Data JPA + Hibernate over PostgreSQL, Flyway migrations
- `jackson-dataformat-xml` for AWS-shaped XML request/response bodies

## Storage

- Object bytes: local disk, content/UUID-addressed, on the `bulk-hdd`
  storage class
- Object/bucket index: PostgreSQL (see
  [`../decisions/0005-postgresql-database.md`](../decisions/0005-postgresql-database.md)),
  on `fast-ssd`

## Dependencies

- Calls out to the IAM service on every request (except `/healthz` and
  `/actuator/**`) via the `iamclient` package for policy evaluation (see
  [`iam.md`](iam.md)) — wired in per `architecture.md` §11 step 3. See
  [`../superpowers/plans/2026-08-22-wire-iam-into-s3.md`](../superpowers/plans/2026-08-22-wire-iam-into-s3.md)
  for what was built and
  [`../superpowers/specs/2026-08-22-wire-iam-into-s3-design.md`](../superpowers/specs/2026-08-22-wire-iam-into-s3-design.md)
  for the design. Fails closed: if IAM is unreachable, times out, or
  errors, the request is rejected (503 `ServiceUnavailable`, which
  S3 clients treat as retryable), never allowed through.

## Multipart upload

| Operation | Request | IAM action |
|---|---|---|
| CreateMultipartUpload | `POST /{bucket}/{key}?uploads` | `s3:PutObject` |
| UploadPart | `PUT /{bucket}/{key}?partNumber=N&uploadId=X` | `s3:PutObject` |
| CompleteMultipartUpload | `POST /{bucket}/{key}?uploadId=X` + `CompleteMultipartUpload` XML | `s3:PutObject` |
| AbortMultipartUpload | `DELETE /{bucket}/{key}?uploadId=X` | `s3:AbortMultipartUpload` |
| ListParts | `GET /{bucket}/{key}?uploadId=X` | `s3:ListMultipartUploadParts` |
| ListMultipartUploads | `GET /{bucket}?uploads` (in-progress only) | `s3:ListBucketMultipartUploads` |

- **Rules (AWS's):** parts 1–10,000; every listed part except the last
  ≥ 5 MiB; each part ≤ 100 MiB (bodies are buffered in memory, like
  single PUTs). Errors `NoSuchUpload`, `InvalidPart`, `InvalidPartOrder`,
  `EntityTooSmall`, `MalformedXML`.
- **ETag:** `md5(concat(binary part md5s))-<part count>`, as AWS.
- **Manifest model:** parts stay as separate blobs; a completed object
  points at its upload (`objects.upload_id`) and GET streams the parts
  in order, opening one at a time. Complete copies nothing.
- **Atomic and idempotent complete:** one Postgres transaction locks
  the upload, validates the part list, drops unlisted parts, upserts the
  object and marks the upload `COMPLETED` — so a crash leaves either the
  whole object or the upload still in progress. Retrying complete on a
  `COMPLETED` upload returns the stored result, so a response lost to a
  crash is safe to retry. Blob deletes happen only after commit, best
  effort.
- **Resumable:** parts survive restarts; a client that lost its upload
  ID finds it with ListMultipartUploads and its parts with ListParts.
- **Content type of the complete body doesn't matter** — `curl -d`
  sends form encoding, and anything calling `getParameter()` would make
  Tomcat consume that body, so the POST route and the auth interceptor
  read the raw query string (`http.QueryParams`). Found by chaos
  scenario 05, not by unit tests (MockMvc never parses bodies).
- **Bucket delete:** `BucketNotEmpty` while uploads are in progress;
  finished upload rows are purged first.

### Reconciler

`MultipartReconciler` runs at startup and every `S3_RECONCILE_INTERVAL`
(default `10m`):

1. aborts `IN_PROGRESS` uploads untouched for `S3_MULTIPART_TTL`
   (default `24h`; each part upload refreshes the clock, and the cutoff
   is re-checked under the row lock);
2. prunes `COMPLETED` uploads no object references and old `ABORTED`
   ones;
3. deletes blob files no row references, and stale `*.tmp` files, once
   older than `S3_RECONCILE_GRACE` (default `1h`, protecting blobs of
   in-flight requests). This also closes the single-PUT orphan window.

Metrics (registered at 0 on startup): `s3_reconciler_uploads_expired_total`,
`s3_reconciler_blobs_deleted_total`, `s3_reconciler_runs_total{outcome}`,
`s3_multipart_uploads_in_progress`. Assumes a single S3 replica.

## Build/test notes

Per `architecture.md` §11: built and tested standalone first (no
auth), then IAM wired in as step 3 — every request now requires a
valid `Authorization: Bearer <jwt>` (obtained from IAM's own
`/auth/token`) except `/healthz`, which remains exempt from the first
commit (`architecture.md` §10), and `/actuator/**`, exempted alongside
it when Actuator/Micrometer was added for observability. S3 exposes
`/actuator/prometheus` (Micrometer/Actuator metrics, unauthenticated
by design so Prometheus can scrape it) and emits JSON-structured logs
via Logback for ingestion by Loki.
